# MPU/I2C regression case: integration session 20261012_235159

Scope: motor-OFF, independent production Policy B, diagnostics disabled.
Preserve the raw captured data at:
`mpu_integration_logs/session_20261012_235159/raw_serial.log`.
Do not overwrite the historical, tool-generated `mpu_integration_report.json`
from this capture: it was produced by the original validator before the
explicit freshness regression gate was introduced.

## Findings

The original host tool emitted `PASS_INTEGRATION_MOTOR_OFF` with
`Reuse > 0.15%` warning. This was **functional acceptance**, not
freshness regression acceptance.

- 225 postcal MINT frames, 224000 compared TIM11 ticks.
- 449 reused gyro ticks = **0.20045%**; 444 ticks with gyro age>1.5ms.
- Worst observed snapshot completion age at TIM11: **2774us**.
- 223771 new gyro samples over those 224000 ticks.
- ZERO I2C error/timeout, UART tx-drop, TIM11 timing-late/gap, postcal
  >3ms invalid-or-expired snapshot ticks.
- Policy B independently attested (`diag=0, ab_diag=0`) and
  4000-sample calibration passed with no retries.

Detailed per-1Hz-frame differences from raw logs:
- 219 / 224 intervals: exactly 999 newly completed gyro samples per
  1000 TIM11 ticks; 5 / 224 intervals: 998 completed samples.
- 223 / 224 intervals: **2 gyro reuses**, 1 interval: 3 reuses.
- No stale `DATA_RDY=0` gyro samples accepted.

This consistent per-second cadence indicates likely acquisition/control
phase synchronization or measurement placement rather than random hardware
I2C errors. It is NOT yet a proven root cause. Code hypothesis:
`last_request_us=now` schedules from actual request start rather than
an absolute 1ms phase, and the integration's `published_sequence`
advances only after full gyro/yaw processing, whereas frozen diagnostic
`diag_fresh_sequence` increments earlier at gyro register completion.
Both can shift reuse at the 1ms consumer. Measure before changing.

## Reference comparability

Frozen diagnostic RC1 `pipeline_20261012_222640`:
- Aggregate reuse: 100 / 227001 = 0.0441% across load stages.
- Stage 0 (no encoder/PID): 62 / 59001 = **0.10508%**.
- Stage 1: 2 / 59000 = 0.00339%.
- Stage 2: 35 / 107000 = 0.03271%.
- RC1 max gyro age observed: 1770us.

Do not equate the integrated 1Hz MINT trace with RC1's staggered UART
and staged load experiments: ISR workload, number/timing of messages,
snapshot sequence publication point and observation windows differ.
The 0.20045% integrated rate exceeds the 0.15% **provisional review**
threshold and is also higher than RC1's stage-0 0.10508%, but this is
not by itself proof that production Policy B is defective.

## Gate correction

The updated `mpu_integration_regression.py` now returns
`REVIEW_FRESHNESS_REGRESSION`, not `PASS_INTEGRATION_MOTOR_OFF`, for
gyro reuse exceeding 0.15%. This is **not** a universal hardware
limit; it is a conservative provisional review gate tied to the
already agreed RC1 regression comparison.

Re-analyze the existing log after `git pull`:

```powershell
python tools/mpu_integration_regression.py --self-test
python tools/mpu_integration_regression.py --folder "mpu_integration_logs/session_20261012_235159"
```

Expect nonzero exit status because freshness review is required.
The tool will rewrite **only the generated JSON report** in the local
log folder; preserve `raw_serial.log` for provenance.
